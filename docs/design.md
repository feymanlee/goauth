# goauth 设计记录

## 已确认的范围

goauth 是独立的 Go 第三方身份认证包，参考 picapica/socialite 的架构重新实现，不复制其代码。

包负责验证第三方凭据并返回统一的第三方身份；站内账号注册、绑定、登录态和业务 JWT 签发由接入方负责，见 [职责边界](adr/0001-authentication-boundary.md)。

首批支持：

| 平台 | 登录场景 |
| --- | --- |
| 微信 | 原生 App 登录 |
| QQ | 原生 App 登录 |
| 抖音 | 原生 App 登录 |
| 微博 | 原生 App 登录 |
| 支付宝 | 原生 App 登录 |
| GitHub | 原生 App 登录（OAuth 授权码） |
| Google | 原生 App 登录（ID 令牌） |
| Facebook | 原生 App 登录（访问令牌） |

所有平台均由原生 App 的客户端 SDK 发起授权，客户端将获得的授权凭据交给业务后端，再由业务后端调用 goauth 完成第三方验证。第一版不负责浏览器授权跳转或 HTTP 回调路由。

## 参考架构的调查结论

参考包实际提供微信和 QQ 的部分身份获取能力，业务层负责站内账号与会话。值得借鉴的是第三方身份与站内账号分离、平台资料归一化，以及同一个平台可配置多个应用实例。

新实现应避免照搬参考包中依赖固定平台分支的构造方式、强制未支持能力并以 panic 失败的接口，以及缺乏平台和应用作用域的身份结果。OpenID 等身份标识不能作为无需校验的登录凭据。

## 已确认的实现方案

- 核心包定义通用 `User`、可独立提取的 `Identity`、错误分类及可复用的能力接口；五个平台分别提供独立适配器。
- 按平台实际支持的能力提供授权码交换或访问令牌验证入口，不强制所有平台实现同一套流程。各平台的具体参数和验证步骤以官方协议核实结果为准。
- `User` 提供 `id`、`nickname`、`name`、`email`、`avatar`、`raw` 和 `token_response`，并保留平台、应用、标识类型与关联标识。ID 统一为字符串，平台不提供的资料为空；不自动合并账号。
- 每个适配器实例对应一份应用配置。同一平台的多个应用通过多个实例接入，不引入全局注册表。
- 对外接口使用标准库类型，所有网络操作支持 context 和可配置的 HTTP 客户端；不绑定 Web 框架、数据库或特定 HTTP 库。
- 按后续确认的通用用户模型，认证成功后的 `User` 保留平台原始资料与令牌响应；失败不返回部分用户或凭据。应用密钥仅用于配置和协议请求，库不把它们添加到用户结果。通过 `User.Identity()` 可提取不含资料和令牌的身份，详见 [User 模型决策](adr/0003-user-and-provider-responses.md)。
- 校验 HTTP 状态、平台错误码、必要身份字段及协议支持的凭据归属信息；HTTP 非成功状态若携带可解析的平台错误码，按平台错误分类，无法解析时才按传输错误处理；不接受仅提交用户标识作为登录证明。
- 交付五个平台适配器、使用说明、最小接入示例及本地模拟服务测试。测试覆盖成功、无效凭据、错误应用归属、异常响应和请求取消；只有平台协议适用的场景才纳入对应测试。
